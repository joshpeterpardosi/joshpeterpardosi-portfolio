Streaming · Card transactions

Real-time fraud detection, scored twice and gated before it ships

Every transaction on a Kafka stream passes a rule engine and, where the features exist, an XGBoost model — and the model is only trusted once it clears a precision/recall bar measured at the exact threshold the consumer flags on.

RoleSolo — design, build, test
TimelineAug 2026
StackKafka, Python, XGBoost, ClickHouse, Grafana, Streamlit, Docker
CodeGitHub repo ↗

1 — The question

Can a transaction be flagged as it happens — and explained afterwards?

Two sources feed one Kafka topic: a synthetic generator with controllable fraud patterns, and a replay of Kaggle's credit-card fraud dataset. Each flag has to say why it fired, and the Kaggle ground-truth label must never reach the live event — a "real-time" detector that has seen the answer proves nothing.

2 — The pipeline

01 · GeneratorProduceSynthetic stream + Kaggle replay → Kafka
02 · RulesCheckAmount over $5,000, more than 5 in 60s, country change
03 · XGBoostScoreReplay events only, flagged at 0.7
04 · ClickHouseStoreBatches of 100 or every 5 s, with a fraud_reason
05 · DashboardsWatchGrafana pipeline health, Streamlit analyst view

3 — The decision that mattered

A release gate is only honest at the threshold that ships

Training refuses to produce a usable model below precision 0.80 or recall 0.70. But the gate scored with model.predict, which applies an implicit 0.5, while the consumer flagged at 0.7. The bar was certifying an operating point the pipeline never ran.

On this model the gap was a single false positive, because it separates cleanly. A weaker model could pass at 0.5 and fail at 0.7 with nothing to catch it. So the threshold now lives in one module that both training and the consumer import, and a test asserts they agree.

The two detection modes are not redundancy. The synthetic stream carries amount, merchant and country; the Kaggle signal lives entirely in 28 anonymised PCA features from its originating bank. The feature spaces don't overlap, so rules judge one source and the model the other — written up as an ADR so it reads as a choice, not an oversight.

4 — What it doesn't do yet

Limit ML scoring covers replayed Kaggle data only. Synthetic traffic is judged by three static rules, which don't adapt to subtler patterns.
Limit Precision 0.856 / recall 0.786 is one held-out split of one public dataset, and its PCA features can't be explained per transaction. Throughput was a demo burst, not a load test.
Verified 49 tests: unit tests run with no Kafka or ClickHouse needed, plus an integration test against the running Docker stack. The combine step alone is covered for rule-only, ML-only, both and neither.
